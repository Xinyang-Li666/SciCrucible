# 主代理–子代理协作协议

> 本仓库所有「审计 → 方案 → 执行 → 验收」类工作默认遵守本协议。
> 依据：2026-10-29～11-06 的实测（外层会话 1.05B tokens 的病根分析、5 篇复核试点、提取 A/B、程序化 coverage 重放）。

## 1. 为什么主/子分离

单一 agent 端到端自主执行的实测病根：

- 消耗 ≈ 步数 × 每步上下文。最大单会话 3,000 次响应、每次输入中位数 233K、总计 7.15 亿 tokens，模型输出只占 0.3%——病根是**历史上下文继承**和**反复自我审计**，不是输出冗长。
- 同一 agent 集「审计者、执行者、验收者」于一身 → 无人独立复核 → 只能靠反复重读自我确认。

分离后（同语料实测）：单会话最大响应数 62、每次输入中位数 33.6K、新会话首输入 27K；复核结果与历史逐条一致。

## 2. 角色与职责

| 角色 | 职责 | 禁止 |
|---|---|---|
| **主代理**（顾问） | 审计现状：读代码/数据，结论必须带文件+行号证据；把决策选项摊给用户；写计划文件（背景写死、改动边界、验收线、回滚）；**独立复核**子代理产出（重跑测试、离线重放、比对哈希）；修正计划 | 不亲自执行批量改动；不跳过证据下结论；不替用户拍板门禁放宽或额度 |
| **子代理**（执行者，如 Codex 全新会话） | 严格按计划文件执行；到停止条件立即停；失败如实记录、不归因猜测 | 重新审计；扩大范围；自动重试；绕过批准；把「工具失败」说成「代码通过」 |
| **用户** | 授权真实模型调用与额度；批准沙盒外命令；拍板门禁放宽与入库 | — |

## 3. 计划文件契约

每次执行前，主代理写一份 `docs/superpowers/plans/<日期>-<主题>.md`，必含：

1. **背景与已定位根因（写死）**：子代理不得重新审计；
2. **全局禁令**：不碰哪些目录/文件、不运行什么；
3. **执行纪律**：只读必要文件、测试重定向到文件、失败两次即停、不做额外自我复查；
4. **分阶段步骤**，每阶段有**可检查的验收线**；
5. **回滚方式**（哪些文件不受 Git 保护，需先备份）；
6. 需要用户授权的步骤（真实调用、门禁放宽、入库）单独标注，默认不执行。

## 4. 会话纪律（已写入 AGENTS.md/CLAUDE.md）

- 一篇文献/一个小批次一个全新会话；不 resume、不 fork；跨批次用交接文件。
- 只发送 `pending-requests.json`；`held-requests.json` 不得发送。
- 不自动重试；conflict/insufficient 不重问。
- 响应 >150 次或单次输入 >150k tokens 时，到安全节点写交接文件开新会话。

## 5. 批准矩阵

| 事项 | 谁批准 | 形式 |
|---|---|---|
| 真实模型调用 | 用户 | 固定来源集常驻 grant 经明确批准可跨篇复用；每批新授权文件/账本绑定 grant 指纹并核来源哈希、模型和额度；超范围再请示 |
| 沙盒外执行（模型子进程写 ~/.codex、写项目外目录） | 宿主审批 | 常驻 grant 不替代宿主审批 |
| 门禁放宽 | 用户 | 必须有数据支撑 + 零调用验证（例：coverage 程序化——41/41 supported 数据 + 五篇重放一致） |
| 入库 commit | 用户单独授权 | 每次 commit 前 |

## 6. 验收闭环

子代理报告 → 主代理**独立**重跑测试、离线重放产物、比对文件哈希与账本 → 全部通过才放下一阶段。不接受「自称通过」。

## 7. 实测踩坑清单（计划文件必须防御）

1. 命令参数要写全（`--typed-input/--profile/--mapping/--render-pdf-regions` 漏一个 = 静默走错契约）。
2. 收集流 prepared 的 `source_root`=项目根 → 下游输出目录必须放项目外，否则撞 overlap 检查。
3. 同一请求换模型跑两臂 → task_id 相同但任务哈希不同 → **必须分账本**。
4. 独占文件先校验后写入（finish 类）；失败不能留下半成品阻挡重试。
5. PNG 渲染含时间戳、字节不恒定 → 复用既有 `source_regions`，不重渲染。
6. 版本号按字符串比较（`'1'/'2'`，不是整数）。
7. 一切估计都要实测推翻：旧代码里的「不要拆束」、A/B 百分比、profile 瘦身上限，都是量了才知道。
8. 验收数字要带口径（单位别名 `um/s ≡ μm/s` 不折算就报「一致数 0」是假阴性）。

## 8. 与现有规则的关系

本协议不替代 AGENTS.md/CLAUDE.md 的领域规则与安全底线（fail-closed、逐字段溯源、不伪造），只是规定**协作方式**；两者冲突时安全底线优先。

## 9. 步骤边界检查器（把「判断」程序化）

反复出现的子代理失败大多是可机械校验的清单问题，而不是需要判断的问题。为此提供确定性检查器 `scripts/batch_check.py`：

```text
python -B scripts/batch_check.py check-prepared <prepared 目录>
python -B scripts/batch_check.py check-cycle <周期目录>
python -B scripts/batch_check.py check-auth --ledger <账本> <授权JSON>
python -B scripts/batch_check.py check-regions --source-root <项目根> <source-regions.json>
```

**强制规则**（替代「失败即停报」）：

1. 子代理在每个步骤边界运行对应检查（准备/计划后 `check-prepared`，冻结后 `check-cycle`，发送前 `check-auth`，渲染后 `check-regions`）。
2. 检查结果分两类：
   - `cataloged`：已知问题，带修复提示——子代理**按提示自行修复一次并重跑检查，不得停报**；
   - `uncataloged`：未知问题——**立即停止并把完整输出报给主代理**。
3. 检查器本身报错（`checker_failed`）也按 uncataloged 处理，不得绕过。
4. 检查器不写任何文件、不调用模型、不联网；每次新踩坑都要沉淀为新的 cataloged 检查项，而不是再写一条文档备忘。

实测：本检查器对第一批工件运行结果——正确的 prepared 目录 clean；误传文件路径、旧 settings 哈希、盲 schema 未枚举 quantity_key 等本批实际失败全部命中 cataloged。
