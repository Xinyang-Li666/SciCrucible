# Codex 独立执行手册（forge-extract 生产线）

> 目标：Codex 在无主代理逐轮裁定的情况下，按本手册 + 协作板独立完成建库批次。
> 主代理降级为每块一次抽查验收；用户保留四类人工关口（见 §5）。

## 1. 会话启动（每次新会话）

1. `python -B scripts/session_handoff.py check --handoff <板上最新交接路径>`；
2. 读 `outputs/alcu-aging/alcu-20-20261109/BOARD.md`：先读「永久规则」块，再读「待执行的最新主代理指令」；
3. 逐字节核对旧内容未变后才追加自己的执行报告块。

## 2. 永久规则（板上与本文一致；冲突以板为准）

- **政策 B′**：时效/固溶/暴露阶段的**过程硬度**与**表格时效序列 t=0 锚点**为 target；孤立静态初始参考值（as-quenched/预变形起算点）、对比合金、文献引用、差值、图注转述为非 target；条件不清楚的标 uncertain。
- **不撒谎底线**：无原文依据的「0 h」不填；时长窗口/约数如实留空或标注；名义组分标 nominal；分析方法未报告如实注明；冲突双值保留并标 source_conflict。
- **证据绑定**：引文逐字符等于冻结切片；跨行拆多片段；省略号展开；行号仅参考；不猜不编。
- **回归四线**（每批必过）：循环基线 26/26 FP0、烧蚀 25/25 FP0、Al–Cu 独立集不回退（当前 33/39）、模板重放（Al–Cu 16+ 钙钛矿 3+ 新模板）。回退即停报主代理。
- **全量测试**：以「无新增」为准；既有环境基线 1F/2E/5skip（alcu_aging_completed_recovery 导入错误、snapshot_alias 错误、exact_failed_task 失败）。
- **环境失败编目**（视为瞬态，不属代码回归）：WinError 5 临时目录 rename；CLI 子进程 export PermissionError；路径过长 WinError 206 / >260 字符派生路径 Errno 2；宿主 Bad Request/传输失败（核验未提交后同范围重试一次）。
- **模型调用**：失败不重发（传输失败例外一次）；账本与授权文件每次调用前核对；预算 0 即停报申请。
- **金标准生产标准流程**：起草（禁用扫描器）→ 模型辅助核对（terra 文字主核 + sol 视觉兜底，逐条 supported/conflict/insufficient）→ 用户只拍板 conflict/insufficient → 标记 reviewed → 后扫描对照更新累计准召。**每攒 5 篇草稿向用户申请一批核对预算（约 8 次）。** 宿主反复出错导致草稿无法完成 → 标「移交主代理」。
- **提交纪律**：块授权范围内可提交（链式 catalog SHA + 每批回执）；超出批次/条数/库范围即停；held/invalid 不升级。

## 3. 每批循环

```
选批（块授权范围内、未处理篇）→ 冻结源核验 → 扫描（正文 v3.1 + 表格 v4+）→ 逐条核实（政策 B′）
→ 模板注册或 admission → 门禁 → 暂存 → 三线回归 + 全量（无新增）
→ 金标准 1 篇：起草（宿主出错移交主代理）
→ 批次执行报告追加板 → 下一批
```

## 4. 硬停点清单

| 情况 | 停给谁 |
|---|---|
| uncataloged 错误 / 科学歧义（0h 推断、归属不明等） | 主代理 |
| 超出块授权（批次/条数/库/来源） | 用户批新块 |
| 金标准 conflict/insufficient | 用户拍板（每批预计 0–3 条） |
| 模型预算用尽 | 用户批新预算 |
| 三线回归回退 | 主代理 |
| 会话临近 150 响应 / 150k 输入上限 | 安全节点写交接并停止 |

## 5. 用户的固定操作清单（独立模式）

1. 批准宿主弹窗（~/.codex 写入、入库写权限）；
2. 批块授权（每 5 批一次，条款模板见板上最近块授权文本）；
3. 批模型核对预算（每攒 5 篇金标准一次，约 8 次调用）；
4. 拍板金标准冲突清单（每批 0～3 条）；
5. 其余全自动；主代理每块一次抽查验收。

## 6. 交接

- 每批/每停点写 handoff 并实际运行 check；新会话只读 next_command 所需文件；
- 执行报告只追加自己的块；逐字节核验板上旧内容未变。

## 7. 模板改动后的漂移处置（2026-11-13 增补）

- 改动任何程序模板后，必须对其全部既有批次（暂存与库内）重跑 `verify_batch` 重放：
  - 重放产物逐字节相同 → 刷新该批 grant 的 rules_sha256 记账（fail-closed 语义刷新已内置于引擎）；
  - 产物不同 → 停报主代理；经用户授权后 store.supersede_batch 替换入账、旧批退休（库内批次历史保留，不导出）；
  - 被替代的暂存目录写 `superseded.json` 标记，重放/冒烟脚本跳过该目录。
- 库本体在每次提交时都按当时模板重验证，因此库内批次不会因后续模板改动而失一致；此规则防的是暂存工件与后续重放口径漂移。
